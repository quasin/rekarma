# ReKarma — agent notes

Distributed recommendation system. Zig 0.17.0 executable linked against librats
(C++ p2p/DHT/bittorrent) built from source by `scripts/fetch-librats.sh`;
Autonomi `ant-client` is installed by `install.sh` for later use. `main.zig`
joins one librats pubsub room and records the last messages it carries into
that room's file (`all.txt` by default), can publish a message handed to it on
the command line, can run itself as a daemon recording the room in the
background, and can mount a release named by a magnet link through FUSE 3 and
serve its files on demand (`--magnet`).

## Layout

    src/main.zig                  executable entry point: args, node, room loop, mode dispatch
    src/room_log.zig              the room's file — last N messages, in memory and on disk
    src/c.h                       every C #include the project needs, in one header
    src/magnet.zig                --magnet: open the session, print the tree, run the mount
    src/magnet_shim.cpp           C++ shim over librats' bittorrent client (metadata, pieces)
    src/magnet_tree.zig           metadata -> directory tree + torrent byte offsets (unit-tested)
    src/magnet_fs.zig             FUSE callbacks: getattr/readdir/open/read/release
    src/fuse_glue.c               libfuse3 glue: fuse_operations, struct stat, mount/loop
    build.zig                     librats guard, translate-c module, g++ shim, fuse3, linking
    build.zig.zon                 package manifest (min zig 0.17.0; .paths = tracked paths only)
    scripts/fetch-librats.sh      builds librats from source into vendor/ (search features ON)
    vendor/librats/               GENERATED by the fetch script — gitignored, never committed
    install.sh                    ant-client installer + fetch-librats.sh
    main.sh                       standalone banner echo (not part of the build)

## Commands

    zig build                                 # link the exe -> zig-out/bin/rekarma
    zig build run                             # build + run a node (blocks until Ctrl-C)
    zig build run -- <args>                   # pass args (run_cmd.addPassthruArgs)
    zig build test                            # unit tests (room_log + magnet_tree)
    zig build -Dlibstdcpp=/path -Dlibgcc_s=/path   # override system C++ runtime paths
    zig build -Dfuse_include=/path -Dfuse_lib=name # override where libfuse3 lives
    bash install.sh                           # ant-client + fetch librats (first setup)
    bash scripts/fetch-librats.sh             # (re)fetch librats after a clone or to bump

`zig build run` starts a real node: it joins the room, listens on the network and
stays up until SIGINT/SIGTERM. Add `-- --help` for the option list, `-- --show`
to print the room's file and exit without starting anything, `-- --daemon` to
start the same node in the background, `-- --version` to print which build this
is without starting anything at all, and `-- "message"` to send one and exit.

## The room and its file

- One room (`rekarma`) and one file (`all.txt`, in the cwd) for everyone by
  default; `--room` / `--file` / `--count` change them. `{room}` in `--file` is
  replaced by the room name, so one file per room needs no wrapper script.
- A message on the command line is a one-shot send: published after a short wait
  for a peer, then the process exits once the reactor has had a moment to put it
  on the wire. `--stay` records afterwards instead, as the program always used
  to. A send never opens the room's file — `load()` rewrites what it is given,
  and a sender that created or trimmed a recorder's log would be a surprise
  (`--file`/`--count` are the recorder's options).
- `rekarma --daemon` is the recording node in the background: one fork plus
  `setsid()` (its own session, so a closing terminal no longer sends it SIGHUP),
  stdout and stderr appended to `<file>.log`, its pid in `<file>.pid`, and
  `kill $(cat <file>.pid)` leaves through the same SIGTERM path as Ctrl-C.
  `--log` / `--pid` move the two files; the cwd is kept, because the room's file
  is resolved against it. The fork happens before `rats_create()` and nowhere
  else: after that call the reactor threads a fork drops are the node's.
- A bare `daemon` word stays what it always was, a message: the mode is the
  `--daemon` flag only, so no room loses the word to the option parser.
- Each line is `<utc stamp> <peer id prefix> <message>`, appended by rewriting
  the file from the in-memory window — that is the only way the cap can drop the
  oldest line.
- The pubsub callback runs on a librats reactor thread and only formats and
  queues; the file is written by the main loop.
- Discovery (DHT + mDNS + peer exchange) is on by default, and its DHT key is
  the room name, so nodes only find others in the same room. `--no-discovery`
  plus `--connect host:port` is how a run is wired by hand.
- NAT traversal is on by default (`--no-nat` disables it): UPnP/NAT-PMP port
  mapping for the listen port and hole punching with rendezvous serving. It is
  what makes a DHT-discovered peer reachable at all; without it the DHT finds
  addresses nothing can dial. `--serve-relay` additionally carries other peers'
  connections, which is the only way two carrier-grade-NAT'd nodes ever meet.

## Discovery: mDNS works where the DHT cannot

Both are on by default and they answer different questions — do not read "no
messages over the DHT" as a code bug until this has been ruled out:

- mDNS advertises the *LAN* address, so two nodes on one network connect with no
  NAT in the path. This is why a two-terminals-on-one-laptop test always passes
  on mDNS and never on the DHT.
- The DHT advertises whatever public address the mesh reports for us. Dialing it
  goes out through the router and back, which only works on a router with NAT
  loopback, and only reaches us at all if the address is really ours — behind
  double NAT/carrier-grade NAT the router's WAN IP (what UPnP reports) and the
  real egress IP (what STUN and the DHT report) differ, and neither is reachable
  inbound.
- `rats_on_dial_failed` is registered, so a discovered-but-unreachable peer is
  printed as `no route to <addr>` instead of silence. That line is the signal:
  discovery and NAT are working, reachability is not.

Debug a layer at a time with `--no-mdns` / `--no-dht` / `--no-discovery`, and
give a sender `--wait` if the DHT needs longer than its default 90 s.

## Mounting a release (`--magnet`)

- `--magnet <link>` is its own mode: no room, no log file, no node, no daemon
  fork — it mounts a torrent read-only through FUSE 3 and serves reads on
  demand. Room-style companions (`--daemon`, `--show`, `--stay`, a message) are
  refused rather than ignored, and `--connect` peers are handed to the torrent as
  well as to the node (the only way to wire a magnet with no trackers/DHT).
- The link may be a full `magnet:?…`, a bare 40-hex/32-base32 info-hash, or
  `xt=urn:btih:…`; `normalize_magnet()` in `magnet_shim.cpp` completes the last
  two. The shell eats `?` and `&`, so the usage text tells the user to quote it.
- Browsing costs nothing: `readdir`/`getattr` answer from the metadata snapshot
  (`bittorrent::Client::torrent_metadata`), and every piece is parked as
  `DontDownload` until a read marks its range (plus 8 pieces ahead) `High`. One
  piece outside the window stays `Normal`, because a picker with nothing wanted
  reports the torrent finished and librats then stops growing its peer set.
- A read blocks in `rek_bt_read` until its pieces verify on disk, which is what
  makes `mpv <mount>/<file>` work on an empty cache. It does not fail on elapsed
  time at all: the 120 s window in `magnet_fs.zig` is the "no progress" report
  interval, and the read only gives up when `num_peers() == 0` or the torrent
  stopped. A player cannot retry a failed read — an error here is exactly "VLC
  stops in the middle of the file" — so the read holds on while anyone can still
  deliver. Progress means fewer missing pieces in this read's own range. While waiting it prints
  `waiting for pieces N..M (… peers)` every 3 s to stderr — in daemon mode that
  is `<cache>/magnet.log`, and it is the only way to tell a slow swarm from a
  hang.
- Priorities are the union of every *active* read's window (`rek_bt.active`,
  guarded by a mutex), not one current window. Seeking starts a second read
  while the first is still blocked; a single window would drop the blocked
  read's pieces and it would sit out its timeout — which reads as "playback
  stops after seeking". Register the range before waiting and remove it in the
  guard's destructor, on every exit path.
- `--magnet --daemon` daemonizes the mount: the fork happens in `main.zig`
  before `rek_bt_open()` (the bittorrent client's reactor threads would not
  survive it), the parent prints pid/log/pid file and `_exit`s, and the child
  keeps serving. Defaults are `<cache>/magnet.log` and `<cache>/magnet.pid`;
  `--log`/`--pid` override them, `--mount` still decides the mount point.
- The FUSE read window is `kPrefetchBytes` (128 MB) past the read, not a piece
  count: a piece count means 256 MB of lookahead on a 4 MB-piece torrent and
  16 MB on a 256 KB-piece one. It also keeps `kKeepBehindPieces` pieces behind the
  start, so a window advancing in 128 KB steps does not discard a piece that is
  halfway through its blocks. `pump_range` only touches pieces entering and
  leaving the window — a full rescan per read is invisible at 400 pieces and
  fatal at 30 000.
- FUSE runs 32 worker threads on purpose: reads block, a player keeps several in
  flight, and every queued request behind them (a lookup from another program
  included) would otherwise wait for pieces it did not ask for.
- The engine is reached through `src/magnet_shim.cpp`, not the C bindings: those
  expose only "add magnet, download everything". The shim compiles against the
  same 3.0.2 headers the library was built from with `private` spelled `public`
  to reach `Torrent::picker_/disk_/peers_`, and touches them only on the reactor
  (via `Reactor::post`). Keep it that way — those members are lock-free.
- Any change to the priority window must keep `update_interest()` being called
  for every peer afterwards: priorities are not interest, and without the
  INTERESTED message a choked peer never serves the piece being waited on.
- `src/fuse_glue.c` owns every FUSE type (`struct fuse_operations`, `struct stat`,
  `fuse_loop_cfg_*`, `FUSE_USE_VERSION 312`); the Zig side sees only paths, sizes
  and byte buffers. Do not translate `fuse.h` into Zig just to remove this file.

## Hard constraints

- **Zig 0.17.0** (`build.zig.zon` `.minimum_zig_version`). No inline `@cImport` —
  C headers are translated into a module by `b.addTranslateC` in `build.zig` from
  `src/c.h`, then imported as `@import("c")`. Add new C includes to `src/c.h`, not
  to Zig files.
- **`librats.a` is GCC-built C++ (`__cxx11` ABI).** It must link the *system*
  libstdc++ and `/usr/lib/libgcc_s.so.1`, not Zig's bundled libc++ (which has no
  `__cxx11`). That is why `build.zig` uses `addObjectFile` for both rather than
  `linkSystemLibrary("stdc++")`. Paths are `-Dlibstdcpp=` / `-Dlibgcc_s=` options.
- **`vendor/librats/` is generated, gitignored, and replaced wholesale by the
  fetch script.** Do not commit anything under `vendor/`; do not try to
  `!`-negate a file inside it (a negation cannot re-include into an ignored
  directory). Anything hand-written lives outside it, in `src/` — the generated
  `features.h` now comes from `cmake --install`, so the old
  `scripts/librats/features.h` shim is gone.
- **librats is built from source, with `RATS_SEARCH_FEATURES=ON`.** The prebuilt
  release archives are configured with it OFF: their `rats_bt_*` entry points are
  stubs returning `RATS_ERR_NOT_ENABLED`, so linking one of those archives makes
  `--magnet` fail at runtime, not at build time. That is why the fetch script
  needs `cmake`/`g++`/`make` and why it does not download a zip any more.
- **`--magnet` needs libfuse3** (`fuse3/fuse.h`, `-lfuse3`) and the C++ shim needs
  the system `g++`: Zig's C++ driver uses the bundled libc++ headers, which do not
  match the `__cxx11` libstdc++ `librats.a` was built against. `build.zig` runs
  `g++ -c` through `addSystemCommand` and links the object into the exe.
- **`build.zig` fails loudly when librats is missing** (`std.Io.Dir.cwd().access`
  on `vendor/librats/librats.a`) instead of a raw linker error. That check resolves
  against the cwd `zig build` was run from (the project root).

## Conventions

- Comments explain *why*, not *what* — every non-obvious choice (translate-c, the
  libstdc++/libgcc_s wiring, the vendoring rule, the features.h shim) carries a
  comment naming the reason. Match that density.
- `.gitattributes` enforces `text=auto eol=lf`; keep files LF.
- `build.zig.zon` `.paths` lists only tracked paths — a generated dir (e.g.
  `vendor`) absent on a fresh clone must not be listed.
- Plain `bash` scripts with `set -euo pipefail`; comment the purpose in a header block.

## Validate a change

    zig build            # must exit 0
    zig build test       # unit tests: the room file's window, the torrent tree
    zig build run -- --help    # prints the banner, the linked librats version/abi and the options
    zig build run -- --version # rekarma's version (from build.zig.zon) and the linked librats'
    zig build run -- --no-discovery -w 1 "smoke"   # a send that exits on its own in ~1 s
    zig build run -- --daemon -f /tmp/rekarma-smoke.txt && kill $(cat /tmp/rekarma-smoke.txt.pid)   # forks, prints its pid, returns at once

`zig build run` alone starts a node and never returns on its own — give it
`--show`, `--help`, `--connect` or a message, or stop it with Ctrl-C. librats'
own INFO logs go to stdout as well, so the default log level is WARN and `-v` is
what turns them visibly on.

Two nodes on one host are wired by hand, because discovery depends on the network
(a public-IP host with no multicast sees no mDNS peer, and the DHT round is 40 s):

    rekarma --daemon -r smoke -f /tmp/rec.txt --no-discovery -p 45001   # recorder
    rekarma "hello" -r smoke --no-discovery -c 127.0.0.1:45001          # sender, exits
    cat /tmp/rec.txt                                                    # the line is there

Stop the daemon with `kill $(cat /tmp/rec.txt.pid)` and its log is
`/tmp/rec.txt.log`.

A mount needs a peer holding the torrent; two processes on one host are enough
if one seeds. With any seeder's info-hash and listen port:

    rekarma --magnet <hash-or-magnet> -m /tmp/mnt --cache /tmp/cache -c 127.0.0.1:6900
    find /tmp/mnt -type f                 # tree from metadata, no payload fetched
    du -sh /tmp/cache                     # small: pieces are parked until read
    tail -c 64 "/tmp/mnt/<file>"          # fetches exactly that piece, then verifies

`--no-dht` keeps such a test off the network; the read of a not-yet-fetched range
is the interesting case, and a hash mismatch there means the file-offset ->
torrent-offset mapping or the cache path convention is wrong.

Playback is the same test with a player, which is what exercises the read
pattern (several reads in flight, seeks to the tail for an index):

    ffmpeg -f lavfi -i testsrc=duration=60:size=640x360:rate=25 -c:v libx264 \
           -preset veryfast -b:v 600k /tmp/vid/movie.mp4   # then torrent /tmp/vid
    cvlc --intf dummy --vout=dummy --aout=dummy --play-and-exit <mount>/rel/movie.mp4

It must play to the end, and `<cache>/magnet.log` must show no `waiting for
pieces` line for long on a LAN seeder.
